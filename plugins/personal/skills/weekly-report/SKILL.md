# 软件研发周报

从 Obsidian、飞书项目、GitLab、GitHub 和本地 Git 收集事实，生成面向主管、对齐飞书项目工作项的中文周报，并在审阅完成后写回 Obsidian。

## 前置条件

| 工具或资源 | 类型 | 必需 | 安装或配置方式 |
| --- | --- | --- | --- |
| Git | `cli` | 是 | `brew install git` |
| Node.js | `cli` | 是 | `brew install node` |
| Obsidian | `system` | 是 | 提供已存在且包含工作日志的 vault |
| `meegle` | `cli` | 是 | `npx @lark-project/meegle@latest install` |
| GitLab MCP | `mcp` | 是 | 在 Codex MCP 配置中启用已安装的 GitLab MCP，设置自建地址和访问令牌，再重启会话 |
| `gh` | `cli` | 是 | `brew install gh`，然后运行 `gh auth login` |

> 加载 Skill 时不要主动检查环境。进入采集流程后执行一次预检；工具缺失、未认证、配置错误或权限不足时停止生成，直接给出表格中的安装或配置步骤，处理完成后再继续。网络超时、远程服务异常等临时故障无论在预检还是采集阶段发生，都按数据源说明降级。

## 工作流

按以下顺序执行：

1. 按日历判定目标周的工作日天数（5 天或月末 6 天）、报告周期和 Obsidian 目标日记。
2. 读取最近一期历史周报。
3. 按 [data-sources.md](references/data-sources.md) 收集并核对所有必需数据源。
4. 合并重复事项，将工作内容对齐到飞书项目的项目、需求、子任务与缺陷，对比上周计划与本周实际。
5. 按 [report-template.md](references/report-template.md) 生成草稿。
6. 等待审阅，确认后写回 Obsidian。

## 工作日与报告周期

- **常规周（小周，5 天）**：周一至周五上班。
- **月末周六上班周（大周，6 天）**：仅当目标周的周六是当月最后一个周六（即 `周六日期 + 7 天` 进入下一个自然月）时，周一至周六上班。
- 直接按目标周的日历判定，不再依赖历史周报推导交替；周报标题保留「小周」或「大周」标记。

报告周期与目标日记按周类型确定：

| 周类型 | 报告周期 | 目标日记 |
| --- | --- | --- |
| 小周（常规 5 天） | 周一 00:00 至周六 00:00，结束时间不包含 | 周五日记 |
| 大周（月末周六上班 6 天） | 周一 00:00 至周日 00:00，结束时间不包含 | 周六日记 |

周日触发时默认处理刚结束的一周。目标周尚未到最后一个工作日时，先说明报告不完整并请求确认；未确认时不要生成。目标日记、vault 或 `## 2 Work Log` 无法唯一定位时请求路径，不要自行创建缺失资源。

## 历史周报

扫描最近 21 天的日记，查找标题 `### 软件研发周报`，从最近一篇提取：

1. 「下周工作计划」，作为计划与实际的比较基准。
2. 项目显示名称、分组方式、语气和格式。

没有历史周报时跳过计划比较。

## 合并与生成

### 数据优先级

| 优先级 | 数据源 | 主要用途 |
| --- | --- | --- |
| 1 | Obsidian 工作日志 | 背景、决策、理由和业务结果 |
| 2 | 飞书项目 | 项目名称、节点子任务、需求与缺陷归属、状态和排期 |
| 3 | GitLab / GitHub | MR、PR 和 Issue 事实 |
| 4 | 本地 Git | 补充遗漏并核对事实 |

按项目、标题、工作项链接、分支和描述判断同一事项。多个来源指向同一工作时合并为一条，不要把工具记录逐条复制进周报。

### 计划完成情况

| 状态 | 处理方式 |
| --- | --- |
| 已完成 | 写入「本周工作总结」 |
| 部分完成 | 在总结中说明进度，并顺延到「下周工作计划」 |
| 未开始 | 写入「其他事项」，已知原因时一并说明 |
| 计划外完成 | 作为新增成果写入「本周工作总结」 |

项目名称优先对齐飞书项目中的「项目」名称和历史周报，条目加粗关键词优先对齐飞书项目下的子任务、需求或缺陷名称，再结合 Obsidian 工作日志、远程活动和本地仓库结构归并。省略本周无活动的项目，不硬编码任何项目名称或项目间关系。

### 内容要求

- 每个项目最多 1 至 2 条，使用 `**加粗关键词**：` 加面向主管的业务语言说明。
- 聚焦主管关心的业务进展、阶段复盘结论、优先级取舍与后续推广计划；不平铺直叙课件章节或代码内部细节。
- 涉及批量导入历史问题或容易引发误解的业务数字时，一句话交代背景与当前真实状态（如已处理完、仅作留痕与后续跟踪）。
- 使用接口数、页面数、配置参数个数和反馈条数等业务数字。
- 省略 commit 数、MR/PR 编号、覆盖率、CI/CD、依赖升级和内部流程细节。
- 中文引号统一使用直角引号 `「」`，嵌套引用使用 `『』`。正文中引用中文项目名、任务名或流程节点名时使用 `「」` 或普通文本，不使用行内代码反引号 `` ` ` ``。
- 下周计划来自顺延事项、飞书项目未完成事项、日记和明确补充的计划。
- 已知时间估算时写为 `（N 天）`；每条说明预期结果，不只写动作名称。
- 「其他事项」只写未开始的顺延事项、交接、阻塞和跨团队配合事项。
- 三个章节必须保留；没有内容时写 `- 无`。

## 审阅与写回

1. 展示完整草稿。
2. 等待反馈并应用修改；未被反馈涉及的条目视为认可，不得删除。
3. 将最终版本写入目标日记的 `## 2 Work Log`。

同一报告周期的标题已存在时替换该章节，否则追加到 `## 2 Work Log` 末尾。不得重复写入同一周期。

## 重要规则

**对齐飞书工作项。** 项目分组与条目名称尽可能对齐飞书项目中的项目、子任务、需求和缺陷名称。

**面向主管汇报。** 说明为什么做、完成了什么、带来什么结果，以及必要的复盘结论与优先级取舍，不直接复制技术记录。

**使用业务数字。** 可以写接口、页面、配置参数和待确认问题数量；不要写 commit、MR/PR 或覆盖率数量。

**沿用历史风格。** 保持连续周报的项目名称、语气、细节层级和格式一致。
